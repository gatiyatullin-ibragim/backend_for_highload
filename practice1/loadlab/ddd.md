# Отчёт по лабораторной работе №1

**Тема:** Базовый сервис на Django — измерение задержек (p50/p95/p99), оценка ёмкости для целевого RPS, сравнение одного крупного инстанса с несколькими маленькими за балансировщиком

**Дисциплина:** Backend для высоконагруженных систем

**Стек:** Python 3, Django, Waitress (WSGI-сервер), Locust (генератор нагрузки), Nginx (балансировщик)

---

## 1. Введение

Цель лабораторной работы — освоить базовый инженерный процесс, применяемый перед запуском высоконагруженной функциональности в продакшене: измерить фактическое поведение сервиса под нагрузкой, разобраться в распределении задержек через percentile-метрики (p50/p95/p99), рассчитать необходимую ёмкость (capacity) для заданной целевой нагрузки (RPS) и сравнить два подхода к масштабированию — вертикальный (один мощный инстанс) и горизонтальный (несколько инстансов за балансировщиком) — при одинаковом суммарном бюджете ресурсов.

Ключевая идея: в highload-инженерии решения о масштабировании принимаются на основе измерений и расчётов, а не интуитивных предположений о том, «сколько серверов понадобится».

## 2. Методология

### 2.1 Тестовый сервис

Реализован на Django, три endpoint'а с разным профилем нагрузки — чтобы отразить реальное разнообразие запросов в системе:

| Endpoint | Назначение | Реализация |
|---|---|---|
| `/ping/` | Базовая линия — оверхед фреймворка и сети | Мгновенный ответ, без вычислений |
| `/cpu/` | Имитация CPU-bound нагрузки | 200 итераций SHA-256 хэширования блока данных |
| `/io/` | Имитация I/O-bound нагрузки (поход в БД / внешний API) | `time.sleep(0.05)` |

### 2.2 Среда запуска

Изначально планировался запуск через Gunicorn, однако Gunicorn не поддерживает Windows (использует Unix-специфичный модуль `fcntl`). Без использования виртуальных машин и Docker в качестве WSGI-сервера применён **Waitress** — нативный Windows-совместимый production-сервер.

```bash
waitress-serve --host=0.0.0.0 --port=8000 --threads=4 loadlab.wsgi:application
```

**Важное методологическое отличие:** Waitress использует многопоточную модель конкурентности (threads), тогда как Gunicorn по умолчанию — многопроцессную (workers/processes). Из-за Global Interpreter Lock (GIL) в CPython потоки не дают настоящего параллелизма для CPU-bound кода — это учтено при интерпретации результатов `/cpu/`.

### 2.3 Инструмент нагрузочного тестирования

**Locust** — выбран за нативную поддержку Python, встроенный расчёт percentile-ов и удобный headless-режим с экспортом в CSV.

```python
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(0, 0)

    @task(3)
    def ping(self): self.client.get("/ping/")
    @task(1)
    def cpu(self): self.client.get("/cpu/")
    @task(1)
    def io(self): self.client.get("/io/")
```

Веса задач (3:1:1) имитируют то, что в реальных приложениях «лёгких» запросов обычно больше, чем «тяжёлых».

### 2.4 Инфраструктура для сравнения топологий

Без Docker и виртуальных машин горизонтальное масштабирование эмулировано несколькими процессами Waitress на разных портах одной машины, объединёнными через нативный Windows-билд **Nginx**:

```nginx
upstream backend {
    least_conn;
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
    server 127.0.0.1:8004;
}
server {
    listen 8080;
    location / { proxy_pass http://backend; }
}
```

### 3.2 Почему percentile-ы, а не среднее

Среднее значение задержки скрывает проблему «хвоста» распределения: если 99 запросов из 100 выполнились за 10 мс, а один — за 5000 мс, среднее покажет около 60 мс и создаст иллюзию нормальной работы. Percentile p99 сразу выявит эту аномалию, поскольку именно он отражает опыт «невезучего» 1% пользователей — паузы сборщика мусора, конкуренцию за ресурсы, блокировки. В индустрии SLA почти всегда формулируются через p95/p99, а не через среднее.

## 5. Оценка ёмкости (capacity estimation) по закону Литтла

### 5.1 Теоретическая база

Закон Литтла связывает три величины:

```
L = λ × W
```

где `L` — среднее число запросов одновременно в системе, `λ` — интенсивность поступления запросов (RPS), `W` — среднее время нахождения запроса в системе (задержка).

### 5.2 Расчёт

1. **Время обработки при низкой конкурентности** (без очередей), измеренное в разделе 3:
   `/io/` ≈ ___ мс

2. **Теоретический потолок пропускной способности** при заданном числе потоков/воркеров:
   ```
   Макс. RPS ≈ число потоков / время обработки одного запроса
   ```
   При 4 потоках и времени обработки ___ с: Макс. RPS ≈ ___

3. **Сравнение теории с практикой** — сопоставление расчётного потолка с фактической точкой излома из раздела 4.2.

4. **Расчёт ресурсов под целевую нагрузку.** Пример для целевого RPS = 500:
   ```
   Нужно инстансов ≈ целевой RPS / измеренный потолок одного инстанса
   ```

> *Подставить фактические цифры и довести расчёт до конкретного числа инстансов с округлением в большую сторону (с запасом).*

## 7. Общие выводы

1. **Dev-сервер непригоден для оценки производительности.** Замеры и capacity-планирование имеют смысл только через production-совместимый WSGI-сервер (в данной работе — Waitress, ввиду ограничений Windows).

2. **Percentile-ы, а не среднее, отражают реальный пользовательский опыт.** p99 выявляет деградации, которые среднее значение маскирует.

3. **Задержка растёт нелинейно с ростом конкурентности** — у любой системы есть точка излома, после которой рост нагрузки приводит к резкому росту задержки из-за накопления очереди. Эта точка и есть практическая ёмкость системы.

4. **Закон Литтла позволяет перейти от единичных измерений к обоснованному расчёту ресурсов** под целевую нагрузку — вместо выбора «с запасом».

5. **Вертикальное и горизонтальное масштабирование дают разные гарантии при равном бюджете ресурсов:** близкая пропускная способность, но принципиально разная отказоустойчивость. Для продакшен-систем с требованием высокой доступности горизонтальное масштабирование предпочтительнее, несмотря на дополнительную сложность (балансировщик, распределённое состояние).

6. **Модель конкурентности сервера имеет значение.** Многопоточная модель (Waitress) и многопроцессная (Gunicorn) по-разному ведут себя на CPU-bound нагрузке из-за GIL в CPython — при выборе production-сервера для Python это следует учитывать отдельно от конфигурации инфраструктуры.
